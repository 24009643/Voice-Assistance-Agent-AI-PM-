# TSB 0.2 Transcript Polish Design

- Status: approved for implementation; automated verification is current, while signed, manual, and release gates remain pending or blocked
- Date: 2026-08-25
- Branch: `codex/wp-04-alpha2`
- Source baseline: `2830c78`
- Parent design: `docs/superpowers/specs/2026-08-20-tsb-v0.2-first-principles-design.md`

## 1. Outcome

Improve mixed Chinese-English dictation without turning cloud availability into a prerequisite for capture. After Stop, TSB may wait up to 1.5 seconds for a narrowly constrained text-only semantic polish. A valid result is copied once; timeout, rejection, missing authorization, or Provider failure falls back to the local final without losing the recording.

Visual redesign is a separate Figma-first track. This design changes the transcript pipeline and its observable states, not the current SwiftUI layout.

## 2. First principles

1. **The user's spoken meaning is the source of truth.** Automatic polishing may apply only objectively verifiable formatting, approved terminology, or a substitution supported by another local ASR candidate. A context-only inference may be retained as a visible review candidate, but it may not be copied automatically. Polishing may not summarize, expand, infer new facts, or change intent.
2. **Local capture must remain useful without cloud access.** Audio capture, live draft, local finalization, persistence, and clipboard delivery cannot depend on a Provider.
3. **Raw evidence is never silently replaced.** Streaming text, offline ASR text, locally cleaned text, and an accepted polished candidate remain distinguishable and traceable.
4. **Clipboard behavior is predictable.** Each successful recording automatically writes to the clipboard exactly once. A late Provider response never replaces that clipboard content.
5. **Latency has a deadline, not a hope.** The semantic-polish wait is bounded to 1.5 seconds. The product records actual Stop-to-local, polish, and Stop-to-copy timings before claiming a 1–2 second experience.
6. **Cloud use is explicit and minimal.** Only text candidates and the user-approved terminology needed for this recording may leave the Mac. Audio, paths, session IDs, the full history library, and secrets are excluded.
7. **Organization is downstream.** Transcript correction finishes or falls back before optional point extraction and association work begins. Organization failure is not transcription failure.
8. **Prefer one reliable correction boundary.** Do not add competing cleaners, hidden rewrite passes, model SDKs, or heuristic candidate fusion without measured evidence.

## 3. Confirmed current behavior and gaps

The current runtime has two ASR passes:

```text
PCM -> Paraformer live/finalized preview
WAV -> SenseVoice offline final
```

After Stop, both complete concurrently. Any nonempty SenseVoice result wins; Paraformer is only a blank/error fallback. `ConservativeCleaner` then trims surrounding whitespace and collapses repeated horizontal whitespace or punctuation. The cleaned result is persisted and copied. Optional organization starts only after that copy and returns points and associations, not a corrected transcript.

Consequences:

- Mixed-language terms such as `TSB` and `Keychain` receive no terminology bias.
- Contextual errors such as an incorrect Chinese homophone receive no sentence-level repair.
- A weaker nonempty SenseVoice result can replace a better Paraformer draft.
- Cloud organization cannot improve the already-copied transcript.
- The existing 20-second organization timeout is unsuitable for the delivery path.

## 4. Transcript artifacts

One recording may produce four distinct artifacts:

| Artifact | Purpose | Mutable | May be copied automatically |
|---|---|---:|---:|
| `streamingText` | Finalized Paraformer candidate and live evidence | No | Fallback only |
| `senseVoiceText` | Offline full-audio candidate | No | Through local selection |
| `localCleanedText` | Selected local candidate plus deterministic cleanup/terminology edits | No | Yes, as fallback |
| `polishedText` | Optional automatically admissible correction | No | Yes, when accepted before deadline |
| `reviewCandidateText` | Optional context-only suggestion requiring user confirmation | No | No |

The record also persists:

- local cleanup edits separately from semantic-polish edits;
- the source selected for clipboard delivery: `local` or `polished`;
- polish terminal state: `notRequested`, `accepted`, `reviewRequired`, `timedOut`, `rejected`, `failed`, or `cancelled`;
- non-sensitive receipt metadata: Provider kind/model, sent character count, elapsed milliseconds, and zero selected-history records.

No existing raw artifact is overwritten to make room for a derived one.

## 5. Stop-to-copy flow

```text
Stop
  -> close capture exactly once
  -> finish Paraformer + run SenseVoice concurrently
  -> apply deterministic local cleanup
  -> save raw candidates and local final
  -> if semantic polish is eligible:
       send both nonempty candidates + approved terms
       wait no more than 1.5 seconds
       validate response
       accepted -> save polished candidate -> copy polished text once
       timeout/reject/fail -> copy local final once
     else:
       copy local final once
  -> persist delivery source/status
  -> enqueue optional organization using delivered text
```

If final local ASR itself fails but finalized streaming text exists, the existing streaming fallback remains. If both are empty or fail, TSB saves the failure and does not call the Provider.

The 1.5-second polish clock starts only after a nonempty local final is durably saved. Stop-to-copy remains a separately measured end-to-end metric; the design does not claim a 2-second total until target-Mac evidence establishes it.

## 6. Deterministic local terminology

Before semantic polish, TSB applies user-approved exact aliases for stable terms such as product names or acronyms.

Rules:

- longest exact match first;
- explicit word/case boundaries for Latin terms;
- no phonetic or fuzzy substitution;
- every replacement creates a terminology edit record;
- ambiguous words require an explicit alias or semantic evidence and are not globally rewritten.

This layer is fast and offline. It repairs stable known terms but is not presented as sentence-level understanding.

## 7. Semantic polish contract

Semantic polish is a new narrow request contract. It reuses the configured OpenAI-compatible HTTPS endpoint, `URLSession`, and endpoint-bound Keychain secret. It does not reuse the organization response schema or its 20-second timeout.

The request uses these fixed limits:

- maximum encoded outer HTTP request body: 64 KiB; maximum inner user-message JSON: 48 KiB;
- maximum encoded outer HTTP response body: 64 KiB; maximum inner assistant `content`: 48 KiB;
- candidates: one or two, ordered `offline` then `streaming`, with maximum 8,000 Unicode scalar values each and 12,000 total;
- terminology entries: at most 64, with one canonical value and at most 8 aliases per entry; include an entry only when its canonical value or an alias occurs exactly in at least one submitted candidate;
- canonical value or alias: at most 80 Unicode scalar values; all terminology text combined: at most 4,096;
- returned corrected text: at most 8,000 Unicode scalar values;
- edits: at most 128; edit original/replacement at most 256 Unicode scalar values each; reason at most 120;
- total changed UTF-16 units: at most 20% of the selected base candidate, rounded up.

The exact request top-level keys are `schema_version`, `request_id`, `candidates`, and `terminology`. A candidate contains exactly `candidate_id`, `text`, and `text_sha256`; a terminology entry contains exactly `canonical` and `aliases`. Candidate IDs are only `offline` and `streaming`. Each hash is lowercase SHA-256 over the exact UTF-8 bytes of `text`.

That inner request is UTF-8 JSON encoded as the `content` of the second Chat Completions message. The outer request contains exactly `model`, `messages`, and `response_format`. `messages` contains exactly two objects with exactly `role` and `content`: the fixed `system` contract first and the inner JSON as the `user` message second. `response_format` is exactly `{"type":"json_object"}`. No streaming, tools, audio, metadata, or additional message is allowed.

The request contains only:

- schema version and random request ID;
- SHA-256 hashes of each submitted candidate;
- nonempty `streaming` and `offline` text candidates;
- the approved terminology entries relevant to the current recording;
- fixed instructions to preserve meaning and perform minimal correction.

It contains no audio, filesystem path, local session ID, history summary, clipboard content, Keychain value, or internal record object.

The strict response top-level keys are `schema_version`, `request_id`, `candidate_hashes`, `base_candidate_id`, `corrected_text`, and `edits`. `candidate_hashes` repeats candidate IDs and hashes in request order, and each item contains exactly `candidate_id` and `text_sha256`. Each edit contains exactly `kind`, `start_utf16`, `length_utf16`, `original`, `replacement`, and `reason`. Allowed kinds are `formatting`, `terminology`, and `candidate_supported`.

The outer Chat Completions response must be a JSON object whose keys are limited to `id`, `object`, `created`, `model`, `choices`, `usage`, and `system_fingerprint`; only `choices` is required. `choices` contains exactly one object whose keys are limited to `index`, `message`, `finish_reason`, and `logprobs`; only `message` is required. `message` contains exactly `role` and `content`, `role` is `assistant`, and `content` is the inner polish-response JSON string. Unknown outer keys, more than one choice, missing/non-string content, or either outer/inner byte-limit breach rejects the result.

The strict response contains:

- matching schema version, request ID, and candidate hashes;
- one corrected text;
- a bounded list of edits with original text, replacement, and short reason.

The Provider is instructed to correct ASR errors, Chinese-English boundaries, casing, punctuation, and terminology only. It must not summarize, answer the speech, add examples, or infer missing facts. HTTPS is required for a remote host; HTTP is accepted only for `localhost`, `127.0.0.1`, or `::1`. Redirects are rejected before any second request can carry text.

## 8. Validation and acceptance

A polish response is accepted only when all checks pass:

1. response size and strict JSON shape are within bounds;
2. request ID and all candidate hashes match;
3. corrected text is nonempty and within the exact limits in section 7;
4. `base_candidate_id` exists, UTF-16 edit ranges are nonoverlapping and in bounds, each `original` exactly matches its base range, and applying the edits reproduces `corrected_text` byte for byte;
5. numbers, URLs, and email addresses are immutable; an approved canonical term may replace only one of its submitted aliases;
6. a `formatting` edit changes only Unicode whitespace, punctuation, or Latin letter case;
7. a `terminology` edit is an exact submitted alias-to-canonical replacement;
8. a `candidate_supported` replacement appears at the corresponding location in the other submitted candidate between unchanged left/right anchors of at least four Unicode scalar values when available; a one-sided anchor is allowed only at a text boundary;
9. edit count and total changed UTF-16 ratio stay within section 7 limits;
10. every unclassified context-only inference is classified locally as `reviewRequired`, persisted separately as `reviewCandidateText`, and excluded from automatic delivery;
11. the request is still current, the session still owns delivery, and the deadline has not expired.

These checks intentionally trade recall for trust. They admit only changes whose mechanics can be verified from local evidence; they do not claim that arbitrary model rewrites are semantically safe. The raw candidates and edit trace remain available for review. A rejected or review-required result falls back to `localCleanedText` for automatic delivery.

## 9. Deadline, cancellation, and clipboard invariants

- Semantic polish has a 1.5-second hard timeout measured from the durable local save with `ContinuousClock`; it is not a claim that total Stop-to-copy is 1.5 seconds.
- The SessionCoordinator owns separate network and deadline task handles. The delivery path never awaits network-task drainage.
- At the deadline, one MainActor-isolated transition validates ownership, reserves the session's only delivery lease for the durable local text, and invalidates the polish request ID. It then copies the already-durable local text and cancels the network handle. A cancellation-insensitive network task may drain in the background, but it cannot block delivery or mutate state when it returns.
- Network success first validates the response off the MainActor. Before any durable mutation, one MainActor-isolated transition rechecks request ID/deadline and reserves the same exclusive delivery lease. Exactly one of deadline or success can reserve it.
- After reserving the lease, the success transition atomically persists the accepted polished text and edit trace. If that save fails, the same lease switches to the already-durable local text, records polish failure when possible, and continues; the deadline path cannot interleave or acquire the lease.
- The leased winning text is durable before the clipboard write. Lease reservation, persistence/fallback, copy, and terminal in-memory state transition execute serially on the MainActor so shutdown cannot interleave after reservation and create an ambiguous side effect.
- Clipboard write occurs once. Provider completion after delivery is ignored and cannot trigger another save-as-current or copy.
- Provider failure never changes a successful local transcript into a failed recording.

Cancellation sequences are distinct:

- recording Cancel before Stop deletes the incomplete recording, starts no polish request, and performs no copy;
- after the durable local save, revoking polish or cancelling its wait invalidates the request and delivers the local text once while the app remains active;
- starting another recording does not supersede an earlier session's delivery gate; each session remains independently owned;
- app shutdown invalidates and cancels outstanding polish work, preserves the durable local record, and performs no new clipboard side effect;
- delivery completion invalidates the request and rejects every late completion.

## 10. Authorization and privacy

Transcript polishing is a new purpose with distinct, default-off `polishEnabled` and `polishConsentVersion` settings. Existing `cloudConsentVersion` for organization can never satisfy polish consent.

Remote HTTPS eligibility requires `polishEnabled == true`, a current `polishConsentVersion`, a valid remote endpoint, and its Keychain secret. Loopback eligibility requires an explicitly enabled loopback polish endpoint but does not require remote-cloud consent or load a Keychain secret. Disabling or revoking polish invalidates current request ownership and clears `polishConsentVersion` without changing organization consent.

Settings must state that:

- current transcript text may be sent for correction;
- audio and recording history are not sent;
- the correction may delay clipboard delivery by up to 1.5 seconds;
- disabling or revoking polish immediately restores local-only delivery.

If revoke or cancellation occurs after dispatch, TSB can stop waiting and reject the response but cannot retract text already received by the Provider. Settings must state this explicitly.

The API key remains in the existing endpoint-bound Keychain store. Logs and receipts contain counts, state, latency, and Provider identifiers only; never candidate or corrected text.

The per-recording `仅本地` choice disables semantic polish and organization for that recording and produces zero remote requests.

## 11. Organization boundary

Organization remains asynchronous and begins after clipboard delivery.

- Its current segment is the exact delivered text: polished when accepted, otherwise local.
- Organization retains its own request ID, input hash, receipt, timeout, retry, and cancellation lifecycle.
- Organization may never rewrite `originalText`, `localCleanedText`, `polishedText`, or the clipboard.
- Organization authorization/failure is presented separately from transcription and polish state.

This separation prevents a slow or failed summary from degrading dictation.

## 12. Observable product states

The pipeline exposes these semantic states for a later Figma-first island design:

1. `recording` — live draft, level, elapsed time, Stop.
2. `finalizingLocal` — offline finalization in progress.
3. `polishing` — local final is safe; bounded semantic correction is running.
4. `deliveredLocal` — fallback/local text copied once.
5. `deliveredPolished` — validated corrected text copied once.
6. `organizing` — optional downstream organization.
7. `organized` — result available.
8. `organizationUnavailable` — delivered text remains safe; retry is secondary.

Figma must cover these states before SwiftUI visual implementation. The current source UI is not modified by this design task.

## 13. Metrics and acceptance evidence

Automated tests must prove:

- exact-alias rules and edit provenance;
- strict request DTO excludes prohibited fields;
- strict response/hash/edit validation;
- accepted polish is saved before exactly one copy;
- a cancellation-insensitive Provider cannot delay the deadline transition or mutate after it is released;
- timeout, malformed output, invalid key, offline, post-local revoke/cancel, and stale completion copy local text exactly once;
- pre-Stop recording Cancel performs zero requests and zero copies;
- app shutdown after local save performs no new copy and preserves the local record;
- late completion cannot mutate the record or clipboard;
- `仅本地` makes zero polish and organization requests;
- organization receives the delivered text and cannot recopy;
- older records decode without polish fields.

Persistence failure tests must also prove:

- local-final save failure starts no polish and performs no copy;
- accepted-polish atomic-save failure immediately falls back to the already-durable local text and copies it once;
- polish receipt/terminal-state update failure cannot stall delivery or authorize copying an untraceable polished value;
- after any clipboard write, restart/recovery never performs an automatic recopy, even if delivery-status persistence failed.

Target-Mac manual acceptance must use user-approved non-sensitive recordings and record:

- Mandarin, Cantonese, and mixed Chinese-English examples;
- `stop_to_local_final_ms`;
- `polish_elapsed_ms`;
- `stop_to_copy_ms` and delivered source;
- immediate clipboard equality;
- original/local/polished record separation;
- exactly zero or one polish request and no unintended organization request;
- visible fallback behavior for offline and timeout.

The user-provided mixed-language comparison becomes a candidate regression case only after explicit consent to retain and annotate it. It is not automatically treated as Golden Set evidence.

Release wording remains evidence-bounded:

- implementation and automated tests do not prove real mixed-language quality;
- one successful DeepSeek call does not prove the 1–2 second target;
- only measured user-present runs may close latency and quality acceptance.

## 14. Implementation ownership and review

Shared transcript lifecycle files remain single-writer. Parallel agents may perform read-only contract review, privacy review, and independent acceptance verification.

Each implementation task closes through:

```text
failing test
  -> minimal implementation
  -> focused test
  -> self-review and commit
  -> independent read-only review
  -> correction and focused rereview if needed
```

Critical or Important findings block the next shared-state task.

## 15. Non-goals

- No cloud audio upload or cloud ASR.
- No automatic Provider/model selection.
- No new SDK or model dependency.
- No fuzzy global replacement dictionary.
- No confidence-based Paraformer/SenseVoice fusion without measured confidence/alignment evidence.
- No automatic clipboard recopy when a late candidate arrives.
- No SwiftUI visual redesign in the transcript-chain implementation.
- No claim that current automated or historical evidence closes the 1–2 second target.

## 16. Decision

Proceed with the bounded semantic-polish architecture above. Preserve local-first delivery, allow at most 1.5 seconds of additional wait, accept only a traceable validated correction, and keep organization downstream. Produce the visual state treatment in Figma before any later SwiftUI redesign.
