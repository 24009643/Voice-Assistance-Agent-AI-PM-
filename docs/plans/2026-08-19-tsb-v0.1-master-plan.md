# TSB 0.1 Implementation Master Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deliver a local-first macOS 0.1 that reliably captures 3–5 minute dictation, supports up to 10 minutes, transcribes Mandarin/Cantonese/mixed Chinese-English with SenseVoiceSmall, preserves the source and copies one local result.

**Architecture:** A native SwiftUI/AppKit shell sends user intents to one `SessionCoordinator`. Audio capture, VAD, offline ASR, cleanup, storage and clipboard delivery are local components with one owner each. OpenDictation is a pinned reference for system-shell behavior; TSB is a new product tree and does not import its cloud-ASR or automatic-paste architecture.

**Tech Stack:** macOS 14+, Swift 6, SwiftUI, AppKit, AVFoundation, Swift Concurrency, Xcode 16+, XcodeGen, XCTest, sherpa-onnx 1.13.6, SenseVoiceSmall int8, macOS Keychain.

**Spec:** `docs/specs/tsb-v0.1-design.md`

## Global Constraints

- Canonical repository path: `/Users/zhuohengchi/Desktop/The Second Brain`.
- Product source path: `apps/macos/TSB`.
- Release bundle identifier: `com.zhuohengchi.tsb`; development identifier: `com.zhuohengchi.tsb.dev`.
- Target validation device: M5 Pro MacBook with 48GB memory.
- Typical recording duration: 3–5 minutes; hard 0.1 limit: 10 minutes.
- 0.1 uses no cloud ASR, no LLM call, no voice wake, no direct cursor insertion and no remote backend.
- Audio, transcripts, model weights, DMGs, build output and credentials never enter Git.
- API configuration supports local Save/Cancel/Delete only and is never read by the 0.1 dictation coordinator.
- `main` is never force-pushed. Every work package is independently testable and revertible.
- The full 0.1 is not implemented as one batch. G0, Alpha, Beta and RC gates are sequential.

## 2. Stable contracts

The following names are frozen before feature work. Detailed fields are introduced in WP-03 with Codable round-trip tests.

```swift
struct SessionID: Hashable, Codable, Sendable { let rawValue: UUID }
struct SessionOrdinal: Comparable, Codable, Sendable { let rawValue: UInt64 }
struct SegmentSequence: Comparable, Codable, Sendable { let rawValue: UInt64 }

struct PCMFrame: Sendable {
    let sessionID: SessionID
    let samples: [Float]
    let sampleRate: Int
    let capturedAt: ContinuousClock.Instant
}

struct SpeechSegment: Sendable {
    let sessionID: SessionID
    let sequence: SegmentSequence
    let samples: [Float]
    let sampleRate: Int
}

struct SegmentTranscript: Codable, Sendable {
    let sessionID: SessionID
    let sequence: SegmentSequence
    let text: String
    let detectedLanguage: String?
    let eventTags: [String]
    let latencyMilliseconds: Int
}

struct CleanResult: Equatable, Codable, Sendable {
    let text: String
    let edits: [EditOperation]
}
```

`SessionCoordinator` is the only component that mutates session lifecycle and automatically delivers text. UI consumes immutable `AppSnapshot` values and sends `UserIntent` values.

### G0: ASR feasibility

WP-02 must prove on the target Mac:

- Mandarin, Cantonese and mixed Chinese-English decode without crash or truncation;
- 3–5 minute and 10 minute samples release all resources;
- RTF is at most 0.5;
- ASR active peak memory increase is at most 2GB;
- sherpa-onnx runtime plus model is at most 500MB;
- model, runtime, VAD, licenses and SHA-256 values are recorded.

Failure stops WP-03–07. UI expansion is not used to hide an unfit ASR baseline.

### Alpha

Toggle shortcut, Escape, local recording, final SenseVoice transcription, conservative cleanup, original-text atomic save and one clipboard delivery work end to end. Cleanup failure delivers the original; disk failure keeps audio; clipboard failure does not repeat ASR.

### Beta

Push-to-talk, VAD stable preview, 3–5/10 minute flows, primary/secondary notch cards and overlapping-session idempotency pass. The older session cannot overwrite a result already delivered by a newer ordinal.

### RC

Retention, recovery, API-profile local CRUD, Golden Set, privacy and stability acceptance pass. There are no LLM, cloud-ASR, Sparkle update, simulated paste or accessibility-permission paths in the 0.1 runtime.

## 4. Multi-Agent execution

### Sol: architect and integrator

- Owns public contracts, plans, ADRs, build/dependency merge points, acceptance decisions and GitHub publication.
- Reviews actual diffs and commands after every work package.
- Does not duplicate Terra's routine Swift implementation.

### Terra: single primary Swift implementer

- Owns the product source tree after WP-01.
- Implements WP-01 and WP-03–06 sequentially so the coordinator, project file and UI state never have multiple writers.
- Requests an interface change instead of editing GPT-5.5 or Luna-owned files.

### GPT-5.5: bounded ASR specialist

- Owns only `probes/sensevoice/`, model bootstrap inputs and the G0 report during WP-02.
- Does not modify the product coordinator or UI.
- After G0, provides the frozen adapter facts to Terra; it does not remain a second product implementer.

### Luna: independent verifier

- Owns fixtures, acceptance runners, evidence templates and read-only privacy/repository audits.
- May add tests only inside its assigned acceptance area; it reports product failures to the file owner instead of patching shared production files.

### Allowed parallelism

- WP-01 and WP-02 can run in isolated worktrees after WP-00.
- After the Alpha contracts are frozen, Luna may build WP-07 fixtures while Terra works on WP-04–06.
- UI state mockups may run beside core implementation only after `AppSnapshot` is frozen.

All other product work is sequential. `project.yml`, dependency locks, app entry, `SessionCoordinator`, shared domain models and entitlements always have one writer.

## 5. Git, evidence and rollback

- Each WP uses `codex/wp-xx-short-name` in its own worktree created from the latest passed gate.
- Each WP ends with focused tests, `git diff --check`, explicit staged-file review and an `EXE-WP-xx.md` update.
- Passing gates receive annotated tags: `tsb-0.1-g0-pass`, `tsb-0.1-alpha-pass`, `tsb-0.1-beta-pass`, `tsb-0.1-rc-pass`.
- Rollback uses `git revert`; no runtime feature-flag framework is added for 0.1.
- Large raw outputs stay ignored. Git stores the environment, command, result summary, commit, model SHA and artifact SHA.

## 6. Golden Set decision rule

The 80-item set follows the approved language slices. A release candidate must satisfy all of the following:

- user-rated “directly pasteable” rate is at least 80%;
- no language slice has more than 10% relative CER regression versus the recorded Whisper Tiny baseline;
- no language slice has more than 5 percentage points regression in critical-entity error rate;
- cleanup makes zero changes to protected numbers, entities, negations or sentence order in the labeled set;
- every regression is reported by slice, never hidden by a total average.

These thresholds are 0.1 acceptance rules, not claims about general model quality.

## 7. Publication sequence

1. Publish the documentation foundation as the first reviewable GitHub version.
2. Publish G0 evidence and the minimal shell after both work packages pass.
3. Publish Alpha, Beta and RC only at their gates.
4. Update the GitHub description to: `本地优先的语音听写与灵感捕捉工具，专注快速、准确、可追溯地记录想法。`
5. Do not publish model weights, user audio, API credentials or generated build artifacts.

The user does not need an interactive app launch for the documentation foundation. Code work still requires non-interactive build and tests before publication; “do not run locally” is not treated as permission to publish unverified code.
